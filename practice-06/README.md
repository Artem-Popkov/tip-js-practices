## Результат и запуск

Браузерный интерфейс получает задачи и категории с учебного API и выполняет создание, редактирование, смену статуса и удаление через HTTP. Сервер — единственный источник данных; localStorage для состояния задач не используется.

Из `practice-06`:

```bash
npm test
npm start
```

Приложение: http://127.0.0.1:5506/; API: http://127.0.0.1:5505/api; вариант: http://127.0.0.1:5506/index.html?dataset=variant. API ПР5 перед этим нужно остановить: он использует тот же порт. Данные API находятся в памяти и возвращаются к исходным после перезапуска.

## Реализация

Общий клиент из ПР5 расширен GET/POST/PATCH/DELETE, нормализацией метода, JSON-телом, Content-Type только при наличии тела и ответом 204→null. GET с телом и неподдерживаемый метод отклоняются до сети. Тайм-аут, внешний AbortSignal, классификация ошибок и очистка ресурсов сохранены.

Доменный API реализует getTasks, getTaskById, getCategories, loadInitialData, createTask, updateTask, setTaskCompleted, deleteTask и resetDemoData. Ответы проверяются по схеме до передачи контроллеру; удаление требует null, сброс — reset=true и корректное total.

form-validation.js возвращает valid/value/errors без доступа к DOM: название после trim длиной 1–100, допустимый приоритет и существующая категория. Карточки создаются через DOM и textContent, без интерпретации пользовательского HTML; категория сопоставляется по id.

Контроллер хранит задачи, категории, фильтры, editingId, AbortController и номер загрузки. Он обращается только к адаптеру view. Состояния: loading перед запросом, ready при непустом ответе, empty при пустом, error при отказе. Повтор после неудачного первого запуска снова загружает категории.

При новой загрузке предыдущий запрос отменяется. Дополнительно сравнивается номер загрузки: старый ответ не может перезаписать свежие результаты, даже если API игнорирует отмену. destroy отменяет загрузку и операции; повторные мутации блокируются. После успешной мутации список запрашивается заново с текущим фильтром, а блокировка снимается в finally. Ошибка мутации не очищает существующие карточки или введённую форму.

Тип проверки указан явно: автоматические сценарии не выдаются за ручной проход с Network. В Safari дополнительно подтверждены отмена удаления (карточка остаётся, всего 12) и перезагрузка после создания «Проверка перезагрузки» (карточка остаётся, всего 13). После проверки штатной кнопкой восстановлено 12 исходных задач. Отдельно остаются быстрые фильтры под throttling в DevTools: в доступных настройках Safari замедление сети не найдено. Автоматические проверки гонки запросов пройдены; этот отдельный ручной пункт не отмечен выполненным. Устная защита ещё предстоит.

## Ответы на контрольные вопросы

1. fetch завершается получением HTTP-ответа и при 404; неуспешный статус нужно проверить через response.ok.
2. У ответа 204 нет JSON-тела: response.json() завершится ошибкой разбора.
3. empty означает успешный запрос с пустой выборкой, error — неуспешную загрузку.
4. Отмена уменьшает лишнюю работу; проверка номера запроса дополнительно защищает от устаревшего ответа.
5. Повторный GET учитывает присвоенный сервером id, нормализацию и актуальный фильтр; локальная догадка не заменяет серверные данные.
